# Min side Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A demo customer account. Visitors log in as Lasse Nielsen with one click, see his order history plus orders they placed themselves, and try account settings that last only for their visit.

**Architecture:**
- **Login:** a shop-only session in a signed httpOnly cookie, separate from Payload's admin cookie. Payload checks the password.
- **Server-rendered pages:** Min side pages read the customer and his visible orders on the server.
- **Browser-only edits:** profile, address and preference edits live in `sessionStorage`.
- **Checkout:** a logged-in checkout links the order to Lasse and remembers its ID in a second signed cookie.

**Tech Stack:** Next.js 16 App Router (read `node_modules/next/dist/docs/` before using Next APIs), Payload 3.92 + Postgres, `@payloadcms/plugin-ecommerce`, Tailwind v4, `lucide-react`.

**Spec:** `docs/superpowers/specs/2026-10-28-min-side-design.md`. Read it first; this plan argues from it.

## Global Constraints

**Copy and data**
- All UI copy is Norwegian bokmål. Use the design reference `MinSide.dc.html` on the Claude Design canvas (https://claude.ai/artifact/VbdTqtVuhwxzNBjDpTHsWN) for layout and copy.
- The demo user is Lasse Nielsen, `lasse.nielsen@eksempel.no`, role `customer`. His password is public and shown on the login page.
- No visitor-typed text may be stored in any order or user record.

**Access**
- Logging in as Lasse must never give `/admin` access.
- Customers must not be able to update their own user record.
- Only users whose roles include `customer` and not `admin` can log in to the shop.

**Isolation between visitors**
- Carts stay per-browser guest carts even when logged in.
- Edits on Min side live in `sessionStorage` and are cleared on "Logg ut".
- Placed-order memory survives logout and lasts about 24 hours.
- These buttons show "Ikke tilgjengelig i demoen" when clicked: Endre passord, Koble fra, Last ned dataene mine, Slett kontoen, Kvittering (PDF), Spor pakken and Returner varer.

**Reuse**
- Reuse `formatPrice`, `formatDate`, `Breadcrumbs`, `orderStatuses`/`statusLabel`, the design tokens in `globals.css`, and the patterns in `src/components/cart/*`.

**Process**
- No git repo exists, so there are no commit steps. Each task ends with a verification step instead.
- Tests are plain `node:assert/strict` modules imported by `tests/unit.test.ts`. They run with `pnpm test`, which is `payload run` and gives TS, `@/` aliases and a live DB. The browser flow is `tests/e2e/min-side.e2e.mjs` (CDP, needs `pnpm dev` running and a fresh `pnpm seed`).
- After code changes, run `graphify update .` (project rule).

## Review Focus

1. **Login redirect target.** A `neste` value like `//evil.com`, `https://evil.com` or `/kassen` must land on `/min-side` (only paths under `/min-side` are allowed). Tested in Task 4.
2. **Order numbers that aren't the visitor's.** Opening `/min-side/ordrer/<n>` for another visitor's checkout order, a guest order or an unknown number must give 404, not someone else's order. Tested in Task 5.
3. **Stale cookies after the nightly reset.** A shop cookie naming a user that no longer exists means logged out, not a crash. Placed-order IDs whose orders were deleted are ignored. Tested in Tasks 4 and 5.
4. **Tampered cookies.** Edited session or order-list cookies are ignored. Tested in Task 1.
5. **An admin's Payload session in the same browser** never counts as a shop login. Tested in Task 4, plus a step in the Task 10 e2e test.

**Interfaces:**
- Produces:
  - `signValue(purpose: string, value: string): string` returns `${value}.${signature}`. The signature is an HMAC-SHA256 of `${purpose}:${value}` keyed with `PAYLOAD_SECRET`, base64url.
  - `readSignedValue(purpose: string, signed: string | undefined): string | null` returns `null` when the input is missing, malformed or tampered, using a timing-safe compare.
- Runner: `tests/unit.test.ts` imports each `tests/*.test.ts` module in turn, prints `ok <file>`, and calls `process.exit(0)`. Any thrown assertion exits non-zero.

### Task 5: Account order data

**Files:**
- Create: `src/lib/account.ts`, `tests/account.test.ts`

**Interfaces:**
- Produces, in `orderReceipt.ts`:
  - `rememberAccountOrder(orderID: number)`: cookie `hylla_mine_ordrer`, purpose `'mine-ordrer'`. The value is IDs joined by `-`, keeping the newest 20. Path `/`, maxAge 24h, httpOnly. Logout does not clear it.
  - `accountOrderIDs(): Promise<number[]>`.
- Produces, in `account.ts`. Pure functions first:
  - `orderProgress(order: Pick<Order, 'status' | 'placedAt' | 'shipping'> & { notes?: Order['notes'] }): { stage: -1 | 0 | 1 | 2 | 3; steps: { label: 'Mottatt' | 'Behandles' | 'Sendt' | 'Levert'; state: 'done' | 'current' | 'todo'; when: string | null }[] }`
    - Status maps to stage: received → 0; processing and on-hold → 1; shipped → 2; delivered → 3; cancelled and refunded → -1.
    - For stage -1, every step is `todo` and the UI shows a closed message instead.
  - `returnDeadline(deliveredAt: string | null | undefined, now: Date): Date | null` returns `deliveredAt` plus 30 days when `now` is on or before that date, otherwise null.
  - `type OrderFilter = 'alle' | 'pagaende' | 'fullforte'`; `parseOrderFilter(value: unknown): OrderFilter`, where unknown values become `'alle'`.
    - `matchesFilter(stage, filter)`: `pagaende` means stage 0–2, and `fullforte` means stage 3 or -1.
- Produces, in `account.ts`. Loaders:
  - `getAccountOrders({ customerID, checkoutOrderIDs }: { customerID: number; checkoutOrderIDs: number[] }): Promise<AccountOrderSummary[]>`.
    - The query is `customerAccount = customerID AND (placedVia = 'seed' OR id IN checkoutOrderIDs)`, sorted `-placedAt`, depth 2 with product gallery populated.
  - `getAccountOrder({ customerID, checkoutOrderIDs, orderNumber }): Promise<AccountOrderDetail | null>` uses the same visibility rule plus `orderNumber`.
  - The builder defines `AccountOrderSummary` and `AccountOrderDetail` from the artboard:
    - number, dates, status label and tone, item text and thumbnails;
    - items, totals, delivery, address and payment;
    - events, which are notes with type ≠ `private`, newest first;
    - `returnDeadline`.
